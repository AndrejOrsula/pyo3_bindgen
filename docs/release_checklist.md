Use this checklist for the maintainer publish/no-publish decision. Evidence is
valid only for one committed release-candidate SHA. A branch head, version
string, prior run, or existing tag is not an implicit candidate. If the
candidate identity or any external evidence cannot be established, choose
`no-publish`.

### Structural check-mode boundary

`release-preflight.sh --check` and `publish-workspace.sh --check` are local,
offline structural checks. These are structural check-mode commands: they
validate executable/configuration shape, exact-version syntax, workspace
metadata, requested-tag/version agreement, and
the local package plan. Before invoking Cargo, both scripts inspect the local
rustup inventory and exact toolchain binaries; Cargo then receives `--offline`.
Both scripts force `RUSTUP_AUTO_INSTALL=0`, so a rustup proxy cannot install a
missing toolchain. They do not require a token, network access, a build, or
publication. A
successful check mode cannot verify the clean candidate commit,
local/public tag existence or peeled equality, exact CI `head_sha`,
workflow-run conclusions, GitHub Actions permissions, branch or tag rules,
environment approvals, crates.io trusted publishing, or security settings.
Record those external items separately as `passed`, `failed`, or `unavailable`.
Never treat a successful `--check` as proof that a tag exists or that a publish
dispatch is safe.

```sh

  --repo "$PUBLIC_OWNER_REPO" \
  --ref "$CANDIDATE_TAG" \
  -f tag="$CANDIDATE_TAG" \
  -f sha="$CANDIDATE_SHA"
```

Invoke both release entrypoints as executables (or explicitly with `bash -p`):
`scripts/release-preflight.sh` and `scripts/publish-workspace.sh`. Plain
`bash script`, `sh script`, and `source script` are unsupported because the
invoking shell can process `BASH_ENV` or import `BASH_FUNC_*` before the
entrypoint can enforce privileged mode.
Do not enable xtrace with `bash -p -x`, `set -x`, or `SHELLOPTS=xtrace` while
supplying release credentials. Bash can expand caller-controlled `PS4` before
the entrypoint's first command, so in-script code cannot prevent that startup
disclosure. Both entrypoints reject xtrace at their first executable line, but
that rejection is only a guardrail; supported release invocation has xtrace
disabled.
The checked-in publication workflow runs these scripts on `ubuntu-24.04`; this
is the supported release environment for their Bash startup scrubber.

## Publish decision

- `publish`: every local and remote gate is green for the exact candidate tags,
  package contents and registry checksums are correct, release notes are honest,
  and the maintainer accepts the exposed API.
- `no-publish`: any gate fails, evidence belongs to another SHA, source/tag
  provenance differs, latest-version checks find material drift, package
  contents are wrong, or the maintainer is not ready to support the API.
